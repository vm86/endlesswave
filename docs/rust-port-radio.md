# Разбивка задач 3.1 и 3.2: состояние радио и цикл микса

Продолжение [rust-port.md](rust-port.md). Основано на чтении `yamusic_radio/dj.py` (HEAD `0576fc1`): класс `Radio` (строки
414–1704), конвейер микса (1706–2060), цикл кодирования и `serve` (3066–3293). Размеры даны в строках Python, которые
надо перенести; в Rust их выйдет заметно больше.

## Что здесь на самом деле

`Radio` — это не один кусок, а пять разных обязанностей в одном классе:

| Обязанность | Python | Строк |
|---|---|---|
| Настройки станции: настроения, жанры, язык, возврат настроек на аккаунте | `start_mood_arc`, `restore_*`, `set_*`, `_release_settings` | ~200 |
| Пул загруженных треков и его чистка | `_wanted`, `_reachable`, `_drop_unwanted`, `_give_up_the_pool`, плейлист на диске | ~250 |
| Очередь: ручной порядок, перестройка, перемещение, удаление, «играть сейчас» | `refresh_queue`, `_set_order`, `queue_*`, `_unpick`, `is_stale` | ~230 |
| Загрузка, выбор и декодирование следующего трека | `_load`, `fill`, `keep_filled`, `prepare`, `_pick`, `next_deck`, `_replay_oldest` | ~350 |
| Состояние и отчёты: пауза, пропуск, часы, статистика, `queue()`, `upcoming()` | `pause`, `request_skip`, `started`, `finished`, `transition`, `queue`, … | ~270 |

Конвейер микса (`mix()` и около десятка функций) отдельно: он принимает `Radio` через узкий протокол `DeckSource`
(7 методов), поэтому его можно переносить и проверять **раньше** самого `Radio`, с поддельным источником дек.

## Решения, которые надо принять до начала

1. **Строгий перенос или с исправлениями.** Есть места, где Python теряет трек: если задача `next_deck` отменена после
   `_pick`, но до готовой деки, кандидат уже вынут из пула и пропадает. Рекомендую **строго как в Python**, исправления
   отдельными коммитами после сверки.
2. **Владение состоянием.** `Radio` в Python однопоточный (asyncio). В Rust предлагаю `Arc<Radio>` с одним
   `std::sync::Mutex<State>`, который **не держится через `.await`** (все долгие операции вне замка), и `tokio::sync::Notify`
   вместо `asyncio.Event`. Актор (канал команд) тяжелее и меняет форму API, пока не нужен.
3. **Как отдавать куски микса.** `mix()` в Python — асинхронный генератор. В Rust: `tokio::sync::mpsc` с ёмкостью 1
   (задача-производитель и потребитель-кодировщик) или трейт `Stream`. Предлагаю канал: проще отмена и счётчик «насколько
   впереди».
4. **Бэкенд-трейт раньше срока.** Для `Radio` нужны `Track`, `MusicBackend`, `Feedback`, `AuthPrompt`. Это задача 5.1, и
   её надо сделать **первой** (см. 3.0), вместе с поддельным бэкендом для тестов.

## Как проверять (общее для всех задач)

`Radio` — состояние плюс время плюс асинхронность, и сравнивать с Python «глазами» нельзя. Нужен общий стенд:

- **Стенд на стороне Python** (`tools/gen_golden.py`, новая функция): поддельный бэкенд из 6–8 синтетических треков
  (WAV-файлы, детерминированные, разные BPM и тональности), **виртуальные часы** (подмена `time.monotonic`/`time.time`
  счётчиком), без случайного шума (`effects=0`). Сценарий — список шагов (вызвать метод, сдвинуть часы, прокрутить
  `mix()` на N кусков); после каждого шага записывается снимок: `queue()`, `skip_info()`, `pause_info()`, статистика,
  содержимое пула и файлов.
- **Стенд на стороне Rust:** тот же поддельный бэкенд (читает те же файлы), `Clock`-трейт с виртуальным временем,
  тот же сценарий из JSON, сравнение снимков.
- Для PCM сравнение по SNR (как в 1.7–1.9); для текста и порядка точное.

Всё, что требует настоящих часов или сети, проверяется отдельными короткими тестами без эталона.

**Результат:** `mix()` работает над любым `DeckSource`, проверен на полном микс-прогоне (6 сценариев: обычный, пропуск, перестройка
очереди в одиночной игре, во время подхода, пропуск вместе с перестройкой, двойная перестройка).

**Что узнали, переносить в 3.1:**
- Приёмник кусков — трейт `PieceSink` (для канала к кодировщикам он реализован на `mpsc::Sender`); тест подставляет свой,
  который меняет радио между двумя кусками, как потребитель генератора в Python.
- Задача `next_deck` в Rust — `NextDeck` (слот с результатом и `JoinHandle`), потому что Python заглядывает в результат
  задачи, не дожидаясь её. Отпущенная задача останавливается (`abort`), как `following_task.cancel()`.
- Деку теперь клонируют (PCM под `Arc`), а в Python это один и тот же объект. Реализация `started(deck)` в `Radio`
  сравнивает `self._next is deck`: в Rust сравнивать нужно по `Arc::ptr_eq(&a.pcm, &b.pcm)` или по номеру деки.

## Риски

1. **Отмена задач.** В Python `next_deck` запускается как задача и отменяется (`following_task.cancel()`), а `_pick` уже
   вынул кандидата. В Rust `JoinHandle::abort()` обрывает на любом `.await`. Надо проверить, что состояние не ломается
   (то же поведение, что в Python, и без утечки файлов).
2. **Тест на времени.** Часть логики зависит от `asyncio.sleep` и реальных таймеров (`REPLENISH_RETRY_SECONDS`,
   `STARTUP_RETRY_SECONDS`). Нужен `tokio::time::pause()` (виртуальное время tokio) или собственный `Clock`; решаю в 3.0.3.
3. **Память.** Дека — это декодированный трек (127 МБ на 6 минут). Нужно владеть PCM без копий: `Arc<[f32]>` и срезы.
4. **Порядок в `Counter.most_common`.** Python сортирует по счёту, при равенстве по порядку вставки; SQL в кэше при
   равенстве «как получится». Статистика сессии должна повторять порядок Python.
5. **Размер.** `Radio` — самая большая часть всего переноса по числу правил поведения; сверка по снимкам сценария — единственный
   надёжный способ не потерять их. Стенд 3.0.4 нужно сделать хорошо.
